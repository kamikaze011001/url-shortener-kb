# Redirect with 302, not 301

A Redirect answers **`302 Found`** with `Cache-Control: private, no-cache` and
`X-Robots-Tag: noindex`. A `301 Moved Permanently` is cached by the browser
indefinitely, which means the second click never reaches this service — and that would
destroy the two properties the product is built on: **Click counts would be
massively undercounted**, and **changing a Destination would be invisible** to anyone
who had already followed the link.

This is not really a technical decision. It is the feature set deciding: statistics
([FR-5](../01-requirements.md)) and mutable Destinations
([ADR-0009](./0009-mutable-destination-with-audit.md)) are both incompatible with a
cached permanent redirect.

## Consequences

- **Every Click costs a request.** The redirect path carries the full traffic
  described in [02-nfr.md](../02-nfr.md), where `301` would have offloaded most of it
  to browser caches for free. That is the price paid, knowingly, and it is the reason
  the redirect path gets a destination cache and a 20 ms p99 budget at all.
- No CDN caching of redirect responses is possible, so an edge-caching strategy
  ([R-7](../06-roadmap.md)) has to move the *lookup* to the edge rather than cache the
  *response*.
- The right long-term shape is to make this a per-Link choice rather than a system-wide
  one: an opt-in "permanent link" mode that answers `301`, in exchange for the Link
  becoming immutable and uncountable — [R-10](../06-roadmap.md). Framing it as a
  product option is more honest than pretending one status code is correct for
  everyone.
